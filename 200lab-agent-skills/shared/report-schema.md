# 200Lab Audit Finding & Report Schema

All audit reports generated by `200lab-*` skills MUST adhere to this uniform schema.

## 1. Finding Item Schema

Each finding must contain the following standardized fields:

```markdown
### [FINDING-{CATEGORY}-{NUMBER}] {Concise Title}
- **Severity**: `CRITICAL` | `HIGH` | `MEDIUM` | `LOW` | `INFO`
- **Location**: `[filepath](file:///absolute/path#L{start}-L{end})`
- **Category**: (e.g. Architecture Modularity, Concurrency, Idempotency, Data Integrity)
- **Evidence**:
  ```code_snippet
  // Exact code extract illustrating the issue
  ```
- **200Lab Rubric Reference**: Quote or identifier from `skill_get` or `ai_tutor`.
- **Architectural Concern / Root Cause**: Technical explanation of why this is a risk.
- **System Impact**: Latency degradation, data corruption, race condition, or single point of failure.
- **Remediation Recommendation**: Specific pattern, pseudocode, or refactoring guidance.
- **Confidence Level**: `HIGH` (90-100%) | `MEDIUM` (60-89%) | `LOW` (<60%)
```

---

## 2. Overall Report Structure

```markdown
# 200Lab {Domain} Audit Report: {Project Name}

## 1. Executive Summary
- Total findings by severity: Critical (X), High (Y), Medium (Z), Low (W)
- Architecture Maturity Score: X/100
- 200Lab MCP Rubric Version: {skill_id}

## 2. Key Findings Matrix (Table)
| ID | Title | Severity | Location | Confidence |
| :--- | :--- | :--- | :--- | :--- |

## 3. Detailed Findings & Technical Analysis
(All finding items following schema above)

## 4. Architectural Roadmap & Recommended Next Steps
- Phase 1: Immediate Reliability Guardrails (P0)
- Phase 2: Structural / Storage Evolution (P1)
- Phase 3: Observability & Resilience (P2)
```
